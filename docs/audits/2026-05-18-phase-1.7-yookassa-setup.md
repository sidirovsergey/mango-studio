# Phase 1.7 G1 — ЮKassa setup + Vercel env ops note

**Status:** operator-driven manual step. Plan task G1 is a pre-flight checklist for H2 (sandbox smoke) and H3 (live cutover). Nothing in code yet — this doc captures the exact env-var matrix the operator needs to apply via Vercel dashboard.

## ЮKassa account prerequisites (F1 + F2 from spec §8)

Operator must complete BEFORE H2 sandbox smoke:

- [ ] Register ЮKassa account at https://yookassa.ru (СМЗ for solo or ИП legal entity)
- [ ] Pass identity verification (typically 1–3 business days)
- [ ] In the ЮKassa dashboard, obtain **sandbox** shop_id + secret_key (separate tab from live keys)
- [ ] In the ЮKassa dashboard, configure webhook URL: `https://mangopro.ru/api/webhooks/yookassa`
- [ ] Subscribe webhook to events: `payment.succeeded`, `payment.canceled`, `payment.waiting_for_capture`
- [ ] Verify sandbox test card numbers from ЮKassa docs (e.g. 4111 1111 1111 1111 for success, 5555 5555 5555 4444 for declined — confirm in dashboard at runtime)

Live shop_id + secret_key are issued post-verification. Required only for H3 cutover.

## Webhook URL — sandbox vs live

The webhook URL is the same for both: `https://mangopro.ru/api/webhooks/yookassa`. The handler accepts both sandbox and live payloads — distinction is enforced by the shop_id + secret_key pair on the incoming POST.

**ЮKassa IP allowlist** in our handler covers both sandbox and live publishing ranges (185.71.76.0/27, 185.71.77.0/27, 77.75.153.0/25, 77.75.154.128/25, 2a02:5180::/32). No URL routing trick needed.

## How H2 (sandbox smoke) will work

1. Operator pushes branch → opens PR `feature/phase-1.7` → Vercel deploys to preview URL (e.g. `phase-1-7-payments-mangopro.vercel.app`)
2. Operator sets Preview env vars per table above
3. Operator visits the preview URL `https://<preview>/upgrade`, clicks "Купить" on 2000 ₽ card
4. Browser redirects to ЮKassa hosted page, operator enters sandbox test card `4111 1111 1111 1111` (or whatever ЮKassa sandbox docs specify)
5. ЮKassa redirects back to `/profile?topup=pending`
6. Operator confirms in Supabase:
   - `billing_payments.status='succeeded'` for the row
   - `user_accounts.balance_kopeks` incremented by 200000 for operator's user_id
7. Operator tries a premium video on preview; should succeed, then verify in DB:
   - `billing_charges.media_job_id=<job>, kopeks=25000, status='reserved'` after submit
   - On scene completion: `status='charged'`, `settled_at` set
8. Operator tries a video with insufficient balance: must get InsufficientBalanceModal opening to /upgrade

## How H3 (live cutover) will work

1. Operator obtains live shop_id + secret_key after verification clears
2. Operator updates Vercel Production env vars per table above (UI=true, GATE_ENFORCE=false)
3. Vercel redeploys production
4. Operator verifies `https://mangopro.ru/upgrade` returns 200
5. Operator tails Vercel logs for ~30 min; confirms `[balance-gate canary]` lines look correct (currently no users have balance, all video attempts would log warns but still proceed)
6. Operator does a real 2000 ₽ top-up with a real card on prod; confirms full flow
7. Operator flips `PAYMENTS_GATE_ENFORCE=true` → redeploys → enforcement live
8. E2E checklist per spec §5

## Rollback plan

If H3 reveals a critical issue:
- Set `NEXT_PUBLIC_PAYMENTS_UI_ENABLED=false` → /upgrade returns 404, ProfileCard / AccountMenu hide top-up links
- Set `PAYMENTS_GATE_ENFORCE=false` → balance gate becomes log-only (users can submit videos without sufficient balance — temporary; not a long-term state)
- Webhook handler remains live but no UI surface drives top-ups, so no new charges land
- Outstanding `billing_payments` with status='pending' can be resolved manually per spec §3.8

DB rollback NOT needed for any non-data-loss issue. `billing_payments` and `billing_charges` are additive; balance_kopeks defaults to 0; trigger only fires on new media_jobs transitions.

## Notes

- 54-ФЗ receipt block is mandatory for live mode (Codex SHOULD-FIX #3). The yookassa-client.ts wrapper always sends it, including in sandbox. ЮKassa accepts it gracefully in sandbox.
- If operator legal status changes from СМЗ to ИП-УСН, `vat_code` in yookassa-client.ts may need updating (currently 1 = "не облагается"). Verify with accountant.
- Idempotence-Key collision risk: deterministic per `(user, package, minute)`. Two users clicking the same package in the same minute have distinct IDs (user prefix). Same user double-clicking the same package within 60s reuses the same key, which ЮKassa de-duplicates server-side.
