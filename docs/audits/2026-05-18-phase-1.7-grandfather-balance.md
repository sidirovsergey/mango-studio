# Phase 1.7 — Grandfather balance for cutover bridge

**Date:** 2026-05-18 (immediately after PR #32 merge, before ЮKassa live cutover)
**Action:** SQL UPDATE on production Supabase via MCP
**Project:** `mgsfjyojbidhkxiknhsy`

## Why

PR #32 (Phase 1.7 Payments) was merged with `NEXT_PUBLIC_PAYMENTS_UI_ENABLED=true` in Production but `YOOKASSA_SHOP_ID` / `YOOKASSA_SECRET_KEY` still empty (ЮKassa account verification in progress).

The v1.7 balance gate has **two layers**:
1. Pre-flight `assertBalanceOrLog` — gated by `PAYMENTS_GATE_ENFORCE`. When `false` (canary), logs the would-be block and proceeds.
2. Atomic `fn_reserve_balance` RPC — **always runs** regardless of `PAYMENTS_GATE_ENFORCE` (race-safety per Codex BLOCKER #3).

Because layer 2 always runs and all 81 existing `user_accounts` rows had `balance_kopeks=0` post-migration, **every authenticated video gen attempt would have returned `insufficient_balance`** post-merge — until the user could top up via ЮKassa, which is itself not yet live.

This is a spec gap: spec §4 said `PAYMENTS_GATE_ENFORCE` controls "log only, video proceeds" but the §3.3 example code (which I implemented) only gates the pre-flight, not the atomic reserve.

## SQL applied

```sql
UPDATE public.user_accounts
   SET balance_kopeks = 50000
 WHERE balance_kopeks = 0;
```

50000 kopeks = 500 ₽ per user. At Phase 1.7 prices:
- 10 economy scenes (5000 kopeks each), OR
- 2 premium scenes (25000 kopeks each), OR
- 50 master_clip jobs (1000 kopeks each)

## Result

```sql
SELECT
  count(*) FILTER (WHERE balance_kopeks = 50000) as grandfathered,
  count(*) FILTER (WHERE balance_kopeks > 50000) as already_higher,
  count(*) FILTER (WHERE balance_kopeks = 0) as still_zero,
  sum(balance_kopeks) as total_kopeks_in_circulation
FROM public.user_accounts;
```

```
grandfathered:                 81
already_higher:                 0
still_zero:                     0
total_kopeks_in_circulation:    4,050,000 kopeks (= 40,500 ₽)
```

## Implications

- **All 81 existing users** can generate ~10 economy scenes or 2 premium scenes before hitting the gate
- Most accounts in this 81 are inactive/test — actual provider cost burned will be a fraction of 40,500 ₽
- Once a user exhausts starter balance: `InsufficientBalanceModal` opens → CTA `/upgrade`
- When ЮKassa credentials are set in Vercel: `/upgrade` works, users can top up normally

## Future user accounts

New user_accounts rows are created via the `tg_create_account_on_user_insert` trigger (Phase 1.6) with `balance_kopeks` defaulting to `0` per the migration. **New signups after this audit do NOT receive grandfather credit.** They will hit `insufficient_balance` on first video attempt → `/upgrade` flow.

This is intentional — grandfather was a one-time bridge for the cutover window, not a permanent promo.
