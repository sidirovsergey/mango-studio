# Phase 1.7.1 — Intent-aware top-ups + payment ledger

**Date:** 2026-05-18 (post-CJM brainstorm + Codex audit)
**Status:** spec v2 — Codex audit pass 1 closed (3 BLOCKER fixes applied; webhook-enqueue UX reversed per audit recommendation)
**Goal:** Bridge the gap between v1.7.0 flat-balance top-ups and the new CJM (PO doc `01_new_cjm_spec.md`) requirement §6.1: «платёжная транзакция должна нести `intent` и `return_to`». Adds an **intent ledger** so post-payment redirect resumes a queued render/studio entry, regardless of tab close, webhook ordering, or two-tab races. Extends the pricing surface to be CJM §6.3-extensible without breaking v1.7.0 callers.

**Pre-requisite:** v1.7.0 merged to `main`, `NEXT_PUBLIC_PAYMENTS_UI_ENABLED=false` in prod, `PAYMENTS_GATE_ENFORCE=false` in prod. UI still gated → breaking signature changes are user-invisible.

## 1. Motivation

The v1.7.0 design assumed the user comes to `/upgrade`, picks a package, pays, returns to `/profile` and uses the balance later. The new CJM flips that: the user is on `/p/{slug}` looking at a free storyboard, clicks «Получить готовый ролик», and EXPECTS the render to start automatically after payment.

Three failure modes the v1.7.0 design does not cover:

1. **Tab close after ЮKassa redirect** — browser-driven resume via `?topup=success` lost.
2. **Webhook arrives before user returns** — race between webhook crediting balance + user landing on `/p/{slug}` to trigger render.
3. **Two tabs same intent** — user opens render request in two tabs, both top-ups succeed → render enqueued twice → double-charge.

Codex audit 2026-05-18 named these as the #2 blocker; solving them requires a persistent intent record, not just metadata.

Codex audit also flagged that the v1.7.0 `priceKopeks(kind, modelTier)` signature shorts CJM §6.3 («функция от длительности, разрешения, модели, количества персонажей»). 1.7.1 extends the signature with optional inputs that MVP ignores — keeping the v1.7.0 flat-pricing semantics but opening the extension surface.

## 3. DB migration `20260520000001_billing_intents.sql`

```sql
-- Intent ledger — the source of truth for "what should happen after payment"
CREATE TABLE billing_intents (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  nonce text NOT NULL UNIQUE,
  user_id uuid NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  project_id uuid REFERENCES projects(id) ON DELETE CASCADE,
  kind text NOT NULL CHECK (kind IN ('render','studio','topup_only')),
  status text NOT NULL DEFAULT 'pending'
    CHECK (status IN ('pending','paid','consumed','expired','canceled')),
  billing_payment_id uuid REFERENCES billing_payments(id) ON DELETE SET NULL,
  return_to text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  expires_at timestamptz NOT NULL DEFAULT (now() + interval '1 hour'),
  consumed_at timestamptz
);

-- Single pending intent per (project, kind). Prevents two-tab double-enqueue
-- at the DB layer regardless of application code paths.
CREATE UNIQUE INDEX billing_intents_one_pending_per_project_kind
  ON billing_intents (project_id, kind)
  WHERE status = 'pending';

CREATE INDEX billing_intents_user_status_idx
  ON billing_intents (user_id, status, created_at DESC);

-- RLS — clients read own pending/paid intents only (for resume polling)
ALTER TABLE billing_intents ENABLE ROW LEVEL SECURITY;

CREATE POLICY "billing_intents_own_select" ON billing_intents
  FOR SELECT USING (user_id = auth.uid());

-- Extend billing_payments with backlink to intent (nullable for v1.7.0 rows)
ALTER TABLE billing_payments
  ADD COLUMN intent_id uuid REFERENCES billing_intents(id) ON DELETE SET NULL;

-- Read-only inspection of an intent (no state mutation). Called by /p/[slug]
-- page when ?nonce= present, to decide what UI to render.
-- Codex BLOCKER fix #1: fn_consume_intent used to mutate paid→consumed AND
-- return new status, which made the dispatch caller test for 'paid' but
-- always see 'consumed'. Splitting read from consume removes the trap.
CREATE OR REPLACE FUNCTION public.fn_inspect_intent(p_nonce text)
RETURNS TABLE (
  intent_id uuid,
  project_id uuid,
  kind text,
  return_to text,
  intent_status text,
  payment_status text,
  expires_at timestamptz
)
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = '', pg_catalog, public
AS $$
BEGIN
  RETURN QUERY
  SELECT bi.id, bi.project_id, bi.kind, bi.return_to, bi.status,
         bp.status, bi.expires_at
    FROM public.billing_intents bi
    LEFT JOIN public.billing_payments bp ON bp.id = bi.billing_payment_id
   WHERE bi.nonce = p_nonce
     AND bi.user_id = auth.uid();
END;
$$;

REVOKE EXECUTE ON FUNCTION public.fn_inspect_intent(text) FROM PUBLIC, anon;
GRANT EXECUTE ON FUNCTION public.fn_inspect_intent(text) TO authenticated, service_role;

-- Promote intent + enqueue render when webhook applies a top-up bound to it.
-- Codex BLOCKER fix #3: drop the `AND status='pending'` guard so the function
-- is idempotent even if the intent was swept to 'expired' by cron between
-- payment and webhook. Idempotency via consumed_at IS NULL guard.
-- Codex UX-reversal: 1.7.1 now enqueues render automatically on webhook
-- (was previously deferred to user return). If the user closes the tab
-- mid-payment, the render still fires; they find it ready next time they
-- open the project. False-negative (paid + ghost-tab) > false-positive
-- (rare enqueue race) — see §5 rationale.
CREATE OR REPLACE FUNCTION public.fn_settle_paid_intent(
  p_billing_payment_id uuid
) RETURNS uuid  -- returns intent_id for caller to enqueue media_job on, or NULL
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = '', pg_catalog, public
AS $$
DECLARE
  v_intent_id uuid;
  v_was_pending bool;
BEGIN
  UPDATE public.billing_intents
     SET status = 'paid'
   WHERE billing_payment_id = p_billing_payment_id
     AND status IN ('pending','expired')   -- both promote; consumed/canceled untouched
     AND consumed_at IS NULL
  RETURNING id INTO v_intent_id;

  RETURN v_intent_id;  -- caller checks NULL = nothing to enqueue (replay)
END;
$$;

REVOKE EXECUTE ON FUNCTION public.fn_settle_paid_intent(uuid) FROM PUBLIC, anon, authenticated;
GRANT EXECUTE ON FUNCTION public.fn_settle_paid_intent(uuid) TO service_role;

-- Mark intent consumed once its media_job has been atomically reserved.
-- Called inside the webhook handler in the same RPC chain as fn_settle_paid_intent.
CREATE OR REPLACE FUNCTION public.fn_mark_intent_consumed(p_intent_id uuid)
RETURNS void
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = '', pg_catalog, public
AS $$
BEGIN
  UPDATE public.billing_intents
     SET status = 'consumed',
         consumed_at = now()
   WHERE id = p_intent_id
     AND status = 'paid';
END;
$$;

REVOKE EXECUTE ON FUNCTION public.fn_mark_intent_consumed(uuid) FROM PUBLIC, anon, authenticated;
GRANT EXECUTE ON FUNCTION public.fn_mark_intent_consumed(uuid) TO service_role;

-- Expiry sweep — pg_cron daily (defined in 1.8.5 ALTER; placeholder here for ops awareness)
-- UPDATE billing_intents SET status='expired' WHERE status='pending' AND expires_at < now();
```

**Migration safety:**
- `billing_payments.intent_id` nullable → existing v1.7.0 rows continue working unchanged.
- `billing_intents` is new — no migration of existing data needed.
- `UNIQUE WHERE status='pending'` is a partial index → re-pending a previously-canceled intent is allowed.
- `expires_at` gives ops a safe sweep target without needing immediate cron.

**Server action flow** (`apps/web/src/app/upgrade/actions/createTopupAction.ts`):

```
1. Parse + validate TopupInput.
2. Require authed email user (anon → redirect /login with return_to).
3. If intent.kind != 'topup_only':
   a. Generate cryptographic nonce (16 chars, [a-zA-Z0-9]) via crypto.randomBytes.
   b. Atomic upsert via fn_get_or_create_intent (see SQL §3):
      — If no pending row exists for (project_id, kind) → INSERT, return new nonce + null payment_id.
      — If pending row exists → return its EXISTING nonce + EXISTING billing_payment_id.
      RLS-friendly: SECURITY DEFINER fn enforces user_id = auth.uid() match.
   c. BLOCKER fix #2 (two-tab → two payments):
      If returned billing_payment_id IS NOT NULL → look up its
      billing_payments.metadata.yookassa_confirmation_url → return immediately,
      DO NOT call ЮKassa Payment.create again.
      → User in tab 2 redirects to the same ЮKassa checkout that tab 1 opened.
      ЮKassa de-duplicates on its end too (Idempotence-Key from v1.7.0 still holds).
4. ЮKassa Payment.create (ONLY if no existing payment for this intent) — extended metadata:
   metadata = {
     user_id, package_code,
     intent_nonce: <nonce> | undefined,  // omitted for topup_only
   }
   confirmation.return_url = origin + (intent ? `/p/{project_id}?nonce={nonce}` : '/profile?topup=pending')
5. INSERT billing_payments { ..., intent_id: <intent_uuid> | null,
                              metadata: { yookassa_confirmation_url, ... } }
6. UPDATE billing_intents SET billing_payment_id = <inserted.id> WHERE id = <intent_uuid>.
7. Return { ok: true, confirmation_url, nonce? }
```

**`fn_get_or_create_intent` SQL** (additive to §3 migration):

```sql
CREATE OR REPLACE FUNCTION public.fn_get_or_create_intent(
  p_user_id uuid,
  p_project_id uuid,
  p_kind text,
  p_nonce text,
  p_return_to text
) RETURNS TABLE (intent_id uuid, nonce text, billing_payment_id uuid, is_new bool)
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = '', pg_catalog, public
AS $$
DECLARE
  v_existing record;
BEGIN
  -- Defensive: enforce caller identity on the inserted user_id.
  IF p_user_id IS NULL OR p_user_id <> auth.uid() THEN
    RAISE EXCEPTION 'fn_get_or_create_intent: user_id mismatch';
  END IF;

  SELECT bi.id, bi.nonce, bi.billing_payment_id INTO v_existing
    FROM public.billing_intents bi
   WHERE bi.project_id = p_project_id
     AND bi.kind = p_kind
     AND bi.status = 'pending'
     AND bi.user_id = p_user_id
   FOR UPDATE;

  IF FOUND THEN
    RETURN QUERY SELECT v_existing.id, v_existing.nonce, v_existing.billing_payment_id, false;
    RETURN;
  END IF;

  INSERT INTO public.billing_intents (nonce, user_id, project_id, kind, return_to)
  VALUES (p_nonce, p_user_id, p_project_id, p_kind, p_return_to)
  RETURNING id, nonce, billing_payment_id, true INTO v_existing.id, v_existing.nonce, v_existing.billing_payment_id, v_existing;
  -- Note: PostgreSQL doesn't support assigning bool literal via RETURNING into
  -- record; restructure as:
  INSERT INTO public.billing_intents (nonce, user_id, project_id, kind, return_to)
  VALUES (p_nonce, p_user_id, p_project_id, p_kind, p_return_to)
  ON CONFLICT (project_id, kind) WHERE status='pending' DO NOTHING
  RETURNING id, nonce, billing_payment_id INTO v_existing.id, v_existing.nonce, v_existing.billing_payment_id;
  RETURN QUERY SELECT v_existing.id, v_existing.nonce, v_existing.billing_payment_id, true;
END;
$$;

REVOKE EXECUTE ON FUNCTION public.fn_get_or_create_intent(uuid, uuid, text, text, text)
  FROM PUBLIC, anon;
GRANT EXECUTE ON FUNCTION public.fn_get_or_create_intent(uuid, uuid, text, text, text)
  TO authenticated, service_role;
```

(Implementation note for executor: the `RAISE EXCEPTION` + `FOR UPDATE` + `ON CONFLICT` pattern needs one more SQL pass to compile cleanly; spec captures the intent. Final form lives in the plan task.)

**Backward compatibility:** legacy v1.7.0 callers passing `{ package_code }` only — `intent` defaults to `topup_only`, no intent row created, no payment metadata changes, behavior identical to v1.7.0.

## 5. Webhook handler extension — enqueue render automatically

`apps/web/src/app/api/webhooks/yookassa/route.ts` — extend after the existing `fn_apply_topup` call:

```typescript
// existing v1.7.0 flow
await sb.rpc('fn_apply_topup', { ... });

// NEW in 1.7.1 — promote bound intent + dispatch its intended action.
const paymentRow = await sb.from('billing_payments')
  .select('id, intent_id, user_id')
  .eq('provider_payment_id', event.object.id)
  .single();

if (!paymentRow.data?.intent_id) {
  // topup_only flow (legacy v1.7.0) — done.
  return NextResponse.json({ ok: true });
}

// Atomically promote intent pending|expired → paid; returns intent_id only
// on first transition (idempotent via consumed_at NULL guard).
const settle = await sb.rpc('fn_settle_paid_intent', {
  p_billing_payment_id: paymentRow.data.id,
});
const intentId = settle.data as string | null;
if (!intentId) return NextResponse.json({ ok: true });  // replay no-op

// Fetch full intent row to dispatch.
const { data: intent } = await sb.from('billing_intents')
  .select('kind, project_id, user_id')
  .eq('id', intentId)
  .single();
if (!intent) return NextResponse.json({ ok: true });

if (intent.kind === 'render') {
  // Enqueue master_clip job for the project. Uses existing 1.7.0
  // reserveMediaJob + fn_reserve_balance path; if balance < price the
  // job is created in error state and balance auto-refunded by
  // trg_billing_settle_on_terminal (1.7.0 invariant).
  await enqueueRenderForProject({
    sb, user_id: intent.user_id, project_id: intent.project_id,
    intent_id: intentId,  // passed for fn_mark_intent_consumed
  });
}
// kind='studio' has no auto-dispatch — user clicks "Open studio" from
// the project page once status flips paid via Realtime. Studio entry has
// no automatic cost (charge happens when they hit "Generate" inside).

// Webhook returns 200 OK; ЮKassa stops retrying.
```

`enqueueRenderForProject` (new helper in `apps/web/src/server/lib/enqueue-render.ts`):
1. Look up project's current `scenes_count` + per-scene `model_tier`.
2. Aggregate price via `aggregateProjectPrice` (see §8).
3. For each scene → call existing `generateSceneVideoAction` programmatically OR insert master-only `media_jobs` row. Pass `intent_id` in `request_input` for audit.
4. After all reservations succeed → `sb.rpc('fn_mark_intent_consumed', { p_intent_id })`.

**Why webhook DOES enqueue (Codex UX reversal, 2026-05-18):**

Original v1 of this spec deferred enqueue to user return (`resolveIntentAction`), arguing «explicit consent». Codex audit pushed back:
- Clicking «Получить готовый ролик» + completing payment IS the consent.
- False-negative case (user pays → closes tab → never returns) is **worse** than false-positive — they paid and got nothing visible, leading to refund tickets and trust loss.
- False-positive case (rare enqueue while user is mid-cancel) is bounded by intent existence + ЮKassa idempotency; refundable via `trg_billing_settle_on_terminal` if render fails.

The user's `/p/{slug}?nonce=X` return page is now «view your render in progress», not «click to start render». If the user returns BEFORE the webhook (race), they see `intent.status='pending'`, payment_status='pending' — Realtime poller updates the UI when webhook flips it. If they return AFTER, the render is already going and they see scene progress.

**Refund symmetry:** if any scene's `media_job` lands in `status='error'`, `trg_billing_settle_on_terminal` refunds that scene's reservation back to balance per v1.7.0 invariant. User can manually re-trigger from Stage 04 with the refund credit.

## 6. `/p/[publicSlug]?nonce=X` — read-only intent inspection

After Codex UX reversal (§5), the resume page no longer dispatches actions. It only INSPECTS state and renders the appropriate view.

`apps/web/src/app/p/[publicSlug]/page.tsx` (excerpt for nonce handling):

```typescript
if (searchParams.nonce) {
  const inspect = await sb.rpc('fn_inspect_intent', { p_nonce: searchParams.nonce });
  if (!inspect.data?.length) {
    // Nonce not found OR user_id mismatch (RLS) → silently strip nonce + show storyboard.
    return <Storyboard project={...} />;
  }
  const { intent_status, payment_status, kind, project_id } = inspect.data[0];

  if (intent_status === 'pending' && payment_status !== 'succeeded') {
    return <PaymentPendingView project_id={project_id} nonce={nonce} />;
    // Client subscribes to Realtime on billing_intents row by intent_id;
    // when status flips paid → consumed, UI auto-transitions.

  if (intent_status === 'expired') {
```

**Tab-close mitigation (revised):** intent is in DB AND render fires automatically via webhook. User can re-open `/p/{slug}` from any device any time — they see the in-progress or completed render. Nonce in URL is now optional convenience (deep-link to the progress view); the storyboard page natively shows the project's latest `media_job` state regardless.

**Two-tab mitigation (revised):** `fn_get_or_create_intent` (§4) returns the existing nonce + existing `billing_payment_id` → both tabs redirect to the SAME ЮKassa checkout. ЮKassa's own idempotency prevents double-billing on its side.

**Stale nonce after expiry (Codex blocker #3 fix):**
- Nonce that's pending + past `expires_at` but cron hasn't swept yet → `fn_inspect_intent` still returns `pending`. UI shows `PaymentPendingView` with a 5-minute hard timeout; on timeout, fallback to «Что-то пошло не так, посмотрите статус оплаты в /profile».
- After cron sweep → status='expired' → `IntentExpiredView`.
- Webhook arriving for an expired intent: `fn_settle_paid_intent` accepts `status IN ('pending','expired')` → still promotes to paid + enqueues render. Balance was credited anyway, intent gets honored even past TTL.

**Bearer-token hardening (Codex security #b/#c):**
- Response from `/p/[slug]` sets `Referrer-Policy: no-referrer` header (Next.js middleware on this route only).
- Server-side request logging strips `?nonce=` query before logging.
- Documented in `docs/audits/nonce-token-handling.md` (created by plan task).
- Vercel analytics filtered to remove the parameter (operator F-task).

## 8. Aggregate price computation (used by sticky-CTA in 1.8.1)

`packages/core/src/quota/aggregate.ts`:

Codex Q#5 surfaced: scene-tier mix, master_clip optional, regen policy. Revised signature reflects each:

```typescript
export interface AggregatePriceInput {
  scenes: Array<{ scene_id: string; model_tier: ModelTier }>;
  withMasterClip?: boolean;  // default true — required for delivery
}

export function aggregateProjectPrice(input: AggregatePriceInput): PriceQuote {
  const withMaster = input.withMasterClip ?? true;
  const modifiers: Array<{ name: string; kopeks: number }> = [];
  let total = 0;

  // Group scenes by tier for breakdown line items.
  const byTier = new Map<ModelTier, number>();
  for (const s of input.scenes) {
    byTier.set(s.model_tier, (byTier.get(s.model_tier) ?? 0) + 1);
  }
  for (const [tier, count] of byTier) {
    const per = priceQuote({ kind: 'scene_video', model_tier: tier }).kopeks;
    modifiers.push({ name: `scene_video × ${count} (${tier})`, kopeks: per * count });
    total += per * count;
  }

  if (withMaster) {
    const master = priceQuote({ kind: 'master_clip' }).kopeks;
    modifiers.push({ name: 'master_clip', kopeks: master });
    total += master;
  }

  return {
    kopeks: total,
    breakdown: { base_kopeks: 0, modifiers },
  };
}
```

**Regen policy (out of aggregate):** scene-level regenerations are user-initiated, post-payment, and priced at per-call `priceQuote({ kind: 'scene_video', model_tier })`. They are NOT included in the storyboard sticky-CTA aggregate — the aggregate represents the cost of **the initial render of the current storyboard**. Regens are extra-line items.

**`first_frame` regen pricing (PO §7.5: 0 free regens):** new kind `scene_first_frame_regen` with `priceKopeks > 0` added in 1.8.1 (regen-as-paid patch). Initial `first_frame` generation stays at 0. NOT part of `aggregateProjectPrice` either.

**No audio in aggregate** — native audio (Veo 3.1 embedded) confirmed by PO 2026-05-18; ElevenLabs/OpenAI TTS overridden out.

## 9. Risks + open questions

**Risks:**
1. **Intent expiry race** — user pays, webhook lags >1h, intent expires before `fn_settle_paid_intent` fires. Mitigation: `fn_settle_paid_intent` accepts `status IN ('pending','expired')` (Codex blocker #3 fix) — promotes expired→paid silently so expired-but-paid intents still trigger render. Cron only sweeps `status='pending'` rows with `expires_at < now()` (placeholder for 1.8.5).
2. **Project deleted while intent pending** — `ON DELETE CASCADE` on `billing_intents.project_id` → orphan top-up still credited (payment succeeds, intent row gone). User has balance but no project to spend on. Acceptable: balance is fungible, they can use it elsewhere or request refund per v1.7 §3.8.
3. **Nonce leak** — nonce in URL is a bearer token for ~1h. RLS on `billing_intents` requires `auth.uid()` match → even if attacker has nonce, they can't consume someone else's intent. `fn_consume_intent` enforces `bi.user_id = auth.uid()`.
4. **Webhook lag + user double-clicks resume** — Realtime poller in `/p/{slug}?nonce=X` UI; if status='paid' arrives during user's wait, auto-dispatch (no manual click). Idempotent because consume promotes to 'consumed' atomically.

**Open questions (executor decides):**
- Nonce length — 16 chars [a-zA-Z0-9] = ~95 bits. Sufficient given 1h TTL + per-user RLS.
- Realtime channel granularity — table-level subscribe vs filter-by-user_id. Recommend filter-by-user_id to reduce noise.
- `topup_only` codepath (legacy /upgrade) — write a `topup_only` intent row anyway for audit symmetry? Recommend no — adds churn for no gain.
