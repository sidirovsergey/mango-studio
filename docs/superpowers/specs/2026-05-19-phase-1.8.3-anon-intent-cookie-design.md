# Phase 1.8.3 — Anonymous → Authed Intent Preservation (Cookie-Based)

**Date:** 2026-05-19 (rev 2 — post-Codex audit)
**Author:** Claude (Opus 4.7)
**Status:** Draft (post-Codex rev — NEEDS-REWORK addressed)

---

## 1. Problem

Public storyboard at `/p/[publicSlug]` shows a sticky-CTA `«Получить ролик»` / `«Открыть Pro-Студию»`. Anon users see the same CTA as authed ones — intentional (Phase 1.8.1 CJM).

Click path for anon:

1. Anon clicks CTA.
2. Client calls `requestRenderAction({projectId, publicSlug})`.
3. Server calls `createTopupAction({...intent...})`.
4. `createTopupAction` sees `user.is_anonymous === true` → `redirect('/login')`.
5. Intent payload (kind/project_id/return_to) **lost**.
6. After OTP verify → `router.push('/')` — anon lands on home, journey breaks.

Real-world: most users drop here.

## 2. Goal

Preserve the intent across the auth detour so the post-login flow lands the user **directly on the ЮKassa confirmation URL** (or pending state) without touching the storyboard again.

## 3. Non-goals

- Not changing `createTopupAction` external semantics (callers from `/upgrade` / `TopupCard` keep their contract).
- Not introducing OAuth or magic-link flows (1.6 OTP stays the auth primitive).
- Not building an "intent management UI" — single pending intent per browser, opaque.
- Not switching CTA UX (sticky stays as-is).
- Not changing `fn_get_or_create_intent` ownership semantics (already enforced — Phase 1.7.1).

## 4. Approach — Topup core extraction + HMAC-signed cookie

### 4.1 Why the rev — Codex audit blocker

Rev 1 of this spec proposed calling `createTopupAction` from inside `verifyOtpAction` after `supabase.auth.verifyOtp` set the session. **Codex audit (2026-05-19) flagged this as a hard blocker:** in Next 15 (which this app actually runs — `next@15.x` per `apps/web/package.json`, NOT Next 16 as rev 1 assumed), a freshly-spawned `getServerSupabase()` client inside the nested action may NOT see the cookies the parent action just set via the `setAll` callback. If `auth.getUser()` returns the anonymous user, `createTopupAction` re-throws `redirect('/login')` — a `NEXT_REDIRECT` thrown all the way up through `verifyOtpAction`, bypassing the planned `{ok:false}` branch, leaving the user stuck.

Rev 2 fix: factor the topup core into a non-redirecting helper that **accepts** an already-authenticated supabase client + user, so the caller controls the auth context.

### 4.2 New file: `apps/web/src/server/lib/topup-core.ts`

```ts
type AuthedUser = { id: string; email: string };
type Supabase = Awaited<ReturnType<typeof getServerSupabase>>;

export async function createTopupForAuthedUser(args: {
  supabase: Supabase;
  user: AuthedUser;
  input: { package_code: TopupPackage; intent: TopupIntent };
}): Promise<CreateTopupResult> { /* never redirects; returns ok/error */ }
```

Body is the lower half of the current `createTopupAction` (from line ~71 onward — intent ledger RPC + ЮKassa Payment.create + billing_payments insert + link). NO `redirect()` calls. Returns `{ok:true, confirmation_url, payment_id, nonce?}` or `{ok:false, error}`.

### 4.3 `createTopupAction` becomes a thin wrapper

```ts
export async function createTopupAction(input): Promise<CreateTopupResult> {
  const parsed = TopupInputSchema.safeParse(input);
  if (!parsed.success) return { ok: false, error: {code:'invalid_package', ...} };

  const supabase = await getServerSupabase();
  const { data: userData } = await supabase.auth.getUser();
  const user = userData.user;
  if (!user || user.is_anonymous || !user.email) {
    redirect('/login');                                  // unchanged for upgrade callers
  }
  return createTopupForAuthedUser({
    supabase,
    user: { id: user.id, email: user.email },
    input: parsed.data,
  });
}
```

External callers (`/upgrade`, `TopupCard`) see no behavior change.

### 4.4 Cookie helper (unchanged design, hardened crypto)

- Name: `mango_pending_intent`
- httpOnly + Secure + SameSite=Lax + Path=`/`
- TTL: 30 minutes
- Value: `<payload_b64>.<hmac_b64>`
  - `payload_b64 = base64url(JSON({kind, project_id, return_to, exp}))`
  - `hmac_b64 = base64url(HMAC-SHA256(payload_b64, secret))` — MAC the **encoded** segment, not the raw JSON (deterministic, canonical).
- Decode: split on `.`, check both halves non-empty, decode HMAC to Buffer, compare to recomputed HMAC with explicit `.length === expected` check then `timingSafeEqual`. Mismatched length → null (do NOT throw).

Payload shape:
```ts
type PendingIntentPayload = {
  kind: 'render' | 'studio';
  project_id: string;        // uuid (validated)
  return_to: string;          // must satisfy TopupInputSchema.return_to constraints
  exp: number;                // unix ms, server-checked on read
};
```

`return_to` validation reuses `TopupInputSchema.shape.intent.shape.return_to` (or extracts the same `.refine` predicates) — not just `startsWith('/p/')`.

### 4.5 Secret discipline

`PENDING_INTENT_SECRET` env var:
- ≥32 bytes raw (the `getPendingIntentSecret()` helper decodes base64 if env value looks base64, else uses raw utf-8 bytes; rejects shorter).
- Missing OR <32 bytes → throw at first call (fail-loud). NOT a silent fallback.
- Documented in `.env.example` with a `openssl rand -base64 48` example value of correct length.
- Dev/test fixture uses a valid 48-byte secret, NOT a literal `"test"` string (Codex SHOULD-FIX #1).

### 4.6 New `intent-actions.ts` flow

```ts
async function detectAnonAndSetCookie(args: {kind, projectId, publicSlug}): Promise<boolean> {
  const supabase = await getServerSupabase();
  const { data: userData } = await supabase.auth.getUser();
  const user = userData.user;
  if (!user || user.is_anonymous || !user.email) {
    await setPendingIntent({ kind, project_id: projectId, return_to: `/p/${publicSlug}` });
    return true;
  }
  return false;
}

export async function requestRenderAction(input): Promise<IntentActionResult> {
  if (await detectAnonAndSetCookie({kind: 'render', ...input})) {
    return { ok: false, error: { code: 'auth_required', message: 'Войдите, чтобы продолжить' } };
  }
  return createTopupAction({ package_code: DEFAULT_TOPUP_PACKAGE, intent: {kind: 'render', ...} });
}
```

Client (StickyCta) on `error.code === 'auth_required'` → `window.location.href = '/login'`.

### 4.7 New `verifyOtpAction` flow

```ts
export async function verifyOtpAction(input): Promise<VerifyOtpResult> {
  /* ... existing input parse + supabase + verifyOtp ... */
  const { data, error } = await supabase.auth.verifyOtp({...});
  if (error || !data.user) return { ok: false, error: {...} };

  // Replay pending intent if any. CRITICAL: pass the existing `supabase` and
  // `data.user` directly into the core — do NOT call createTopupAction (which
  // spawns a fresh SSR client that may not see the just-set cookies).
  const pending = await consumePendingIntent();   // reads + deletes cookie atomically
  if (!pending || !data.user.email) {
    return { ok: true, user_id: data.user.id };
  }
  const replayInput = {
    package_code: DEFAULT_TOPUP_PACKAGE,
    intent: { kind: pending.kind, project_id: pending.project_id, return_to: pending.return_to },
  };
  const parsed = TopupInputSchema.safeParse(replayInput);
  if (!parsed.success) {
    console.warn('[verifyOtp] replay payload invalid', { event: 'replay_invalid' });
    return { ok: true, user_id: data.user.id };
  }
  const result = await createTopupForAuthedUser({
    supabase,
    user: { id: data.user.id, email: data.user.email },
    input: parsed.data,
  });
  if (!result.ok) {
    // Most common: ownership check fails (cookie originated for a project
    // not owned by THIS user — e.g. shared device + different account login).
    console.warn('[verifyOtp] replay topup failed', {
      event: 'replay_topup_failed',
      code: result.error.code,
      kind: pending.kind,
    });
    return { ok: true, user_id: data.user.id };
  }
  return { ok: true, user_id: data.user.id, next_url: result.confirmation_url };
}
```

`LoginForm.onVerifyCode` on `r.ok && r.next_url` → `window.location.href = r.next_url`. Else fall through to existing `router.push('/'); router.refresh()`.

### 4.8 Defence-in-depth

Even if a cookie is stolen + replayed by user Y who didn't originate it:
- `fn_get_or_create_intent` enforces `projects.user_id = auth.uid()` → `insufficient_privilege` for non-owners. (Phase 1.7.1 closed this.)
- Cookie can't fabricate payment — `billing_payments` row is bound to current `auth.uid()` by the topup core.
- HMAC mismatch on tamper → reject silently.
- Expired → reject silently.

Cookie is a **UX helper**, not a security gate.

### 4.9 Logging discipline (Codex SHOULD-FIX #3)

Allowed log fields:
- Stable event name (e.g. `'replay_topup_failed'`)
- Error code (DB error codes, our internal codes — never DB messages)
- Intent kind (`'render'` / `'studio'`)
- Short prefix hash of project_id (first 8 hex of `sha256(project_id)`) — debugging without correlation across logs
- NO secret, NO full cookie value, NO confirmation_url, NO raw DB exception message, NO user_id/email

## 6. Tests

### 6.1 `pending-intent-cookie.test.ts` (unit)

- encode → decode roundtrip
- HMAC tampered (mutate one byte of HMAC suffix) → null
- Payload tampered (mutate one byte of payload prefix) → null
- HMAC length mismatch (truncate by 1 byte) → null, no throw
- Expired (`exp < now`) → null
- Malformed (no `.`, empty, wrong base64) → null
- Rotated secret (encode with secret A, decode with secret B) → null
- Invalid payload shape (kind not in enum, project_id not uuid, return_to violates schema) → null
- Missing `PENDING_INTENT_SECRET` env → `setPendingIntent` throws "PENDING_INTENT_SECRET not set"
- Weak secret (<32 bytes) → throws "PENDING_INTENT_SECRET too short"

### 6.2 `intent-actions.test.ts` (integration)

- `requestRenderAction` anon (mock `auth.getUser → {is_anonymous: true}`) → cookie set in response + result `{ok:false, code:'auth_required'}` + does NOT call `createTopupAction`.
- `requestRenderAction` authed (mock authed user with email) → cookie NOT set + delegates to mocked `createTopupAction` returning fixture.
- `openProStudioAction` mirrors both.

### 6.3 `verifyOtpAction.test.ts` (integration)

- No cookie + valid OTP → `{ok:true, user_id, next_url:undefined}` (existing tests stay green).
- Valid cookie + valid OTP + ownership-OK project → mocked `createTopupForAuthedUser` returns success → `next_url` present + cookie deleted in response headers (`Set-Cookie: mango_pending_intent=; Max-Age=0`).
- Expired cookie + valid OTP → `consumePendingIntent` returns null → no replay → no `next_url` + cookie still gets `Max-Age=0` clear-on-read.
- Tampered cookie + valid OTP → same as expired (null + clear).
- Old-secret cookie + valid OTP → same as expired (null + clear).
- Valid cookie + valid OTP + `createTopupForAuthedUser` returns `{ok:false}` (ownership fail simulation) → cookie consumed + login succeeds without `next_url` + warn log emitted with allowed fields only.

### 6.4 Same-request session visibility (Codex BLOCKER #3 — falsifying experiment)

`same-request-session.test.ts` (NEW). Boots a Next test request, calls `supabase.auth.verifyOtp` with a known seeded user, then immediately in the same handler scope creates a fresh `getServerSupabase()` client and calls `auth.getUser()`. Asserts the returned user.id matches the verified user, not anonymous.

**If this test passes** → the rev 1 nested-action approach would have worked, but the rev 2 core extraction is still the cleaner design. Keep it.

**If this test fails** → confirms the Codex hypothesis; the rev 2 core extraction is required, and we document this in a feedback memory.

## 7. Operator deploy steps

1. Generate secret: `openssl rand -base64 48`.
2. Add `PENDING_INTENT_SECRET` to Vercel prod env (Production + Preview scopes).
3. Redeploy.
4. Smoke: anon on /p/{slug} → CTA → /login → OTP → land on ЮKassa-test.

No DB migration. No new tables. No backfill.

## 8. Risk

- **Cookie size** — payload ~150 bytes encoded + HMAC ~43 chars base64url (SHA-256 = 32 bytes → 43 chars). Total cookie ~200 bytes. Below all limits.
- **Secret rotation** — out of scope tooling; rotation invalidates all in-flight cookies (acceptable, max 30min impact). Document in operator runbook.
- **SameSite=Lax** — OTP verify is same-origin POST → cookie attached. No issue.
- **ЮKassa redirect lifetime** — confirmation_url TTL ~1h. 30min cookie + remaining time is well under.
- **Multi-tab race** — tab B's `setPendingIntent` overwrites tab A's. After login, only tab B's intent fires. Acceptable.
- **Stale cookie on aborted CTA** — accepted UX. 30min TTL bounds it. Optional future: explicit "cancel pending action" affordance on /login.
