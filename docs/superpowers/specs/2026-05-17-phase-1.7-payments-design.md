# Phase 1.7 — Payments (credit balance + ЮKassa top-ups)

**Date:** 2026-05-17 (brainstorm done immediately after v1.6.2 ship)
**Status:** spec draft (awaiting Codex audit pass)
**Goal:** Replace the binary `premium` tier in v1.6 with a per-user kopek-precision **credit balance** that gates video generation. Top-ups via **ЮKassa** (RU карты + СБП). No subscription in 1.7.

## 1. Motivation

v1.6 shipped tier-based gating with `trial / free / premium` enum on `user_accounts`. The original plan had Phase 1.7 = "wire payments to flip tier to premium" (monthly subscription).

User pivoted during 1.7 brainstorm (this session): replace the subscription model with **prepaid credit balance**. Rationale:
- Lower commitment for first-time users (one-time top-up, not recurring)
- Marketplace alignment — Russian B2C audience prefers credit packages to subscriptions
- Pricing flexibility — each video model has different cost basis (Seedance vs Veo vs Grok Imagine differ ~10x in per-generation cost); credits give us per-operation pricing without renegotiating a subscription tier
- Refund simplicity — credits don't expire; if user is unhappy we just zero the row, no proration

The tier-based capability matrix from v1.6 stays as a **fallback discriminator** for non-paid features (legacy audio kinds, internal kinds), but the user-visible video gate becomes balance-based.

## 3. Components

### 3.1 New DB schema (`supabase/migrations/20260518000002_billing.sql`)

```sql
-- Add balance to user_accounts (kopeks for atomic precision; $1 ≈ 100 RUB ≈ 10000 kopeks)
ALTER TABLE user_accounts
  ADD COLUMN balance_kopeks bigint NOT NULL DEFAULT 0 CHECK (balance_kopeks >= 0);

-- Payment intents (one per ЮKassa Payment.create call)
CREATE TABLE billing_payments (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id uuid NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  provider text NOT NULL DEFAULT 'yookassa' CHECK (provider IN ('yookassa')),
  provider_payment_id text NOT NULL UNIQUE,  -- ЮKassa idempotency key
  amount_kopeks bigint NOT NULL CHECK (amount_kopeks > 0),
  currency text NOT NULL DEFAULT 'RUB' CHECK (currency IN ('RUB')),
  status text NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','succeeded','canceled','failed','refunded')),
  package_code text NOT NULL CHECK (package_code IN ('topup_2000','topup_5000','topup_10000')),
  created_at timestamptz NOT NULL DEFAULT now(),
  succeeded_at timestamptz,
  metadata jsonb NOT NULL DEFAULT '{}'::jsonb  -- ЮKassa raw response
);

CREATE INDEX billing_payments_user_id_created_at_idx
  ON billing_payments (user_id, created_at DESC);

-- Charges (one per completed media_job that consumed balance)
CREATE TABLE billing_charges (
  media_job_id uuid PRIMARY KEY REFERENCES media_jobs(id) ON DELETE CASCADE,
  user_id uuid NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  kopeks bigint NOT NULL CHECK (kopeks > 0),
  kind text NOT NULL,         -- denormalised media_jobs.kind for analytics
  model_tier text,            -- 'economy' | 'premium' | null
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX billing_charges_user_id_created_at_idx
  ON billing_charges (user_id, created_at DESC);

-- RLS: clients read own rows only; writes via SECURITY DEFINER
ALTER TABLE billing_payments ENABLE ROW LEVEL SECURITY;
ALTER TABLE billing_charges  ENABLE ROW LEVEL SECURITY;

CREATE POLICY "billing_payments_own_select" ON billing_payments
  FOR SELECT USING (user_id = auth.uid());

CREATE POLICY "billing_charges_own_select" ON billing_charges
  FOR SELECT USING (user_id = auth.uid());

-- Atomic top-up function (called from webhook with service_role)
CREATE OR REPLACE FUNCTION public.fn_apply_topup(
  p_payment_id uuid,
  p_user_id    uuid,
  p_kopeks     bigint
) RETURNS void
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = '', pg_catalog, public
AS $$
BEGIN
  -- Idempotency: mark payment succeeded; if already succeeded, no-op
  UPDATE public.billing_payments
     SET status = 'succeeded',
         succeeded_at = COALESCE(succeeded_at, now())
   WHERE id = p_payment_id
     AND status = 'pending';

  IF NOT FOUND THEN
    -- Either already succeeded (replay) or status moved to failed/canceled (terminal mismatch)
    RETURN;
  END IF;

  UPDATE public.user_accounts
     SET balance_kopeks = balance_kopeks + p_kopeks
   WHERE user_id = p_user_id;
END;
$$;

-- Atomic charge-on-success function (called from media_jobs trigger)
CREATE OR REPLACE FUNCTION public.fn_charge_balance(
  p_job_id  uuid,
  p_user_id uuid,
  p_kopeks  bigint,
  p_kind    text,
  p_model_tier text
) RETURNS void
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = '', pg_catalog, public
AS $$
DECLARE
  v_existing int;
BEGIN
  -- Idempotency: skip if already charged
  SELECT 1 INTO v_existing FROM public.billing_charges WHERE media_job_id = p_job_id;
  IF FOUND THEN RETURN; END IF;

  -- Atomic decrement: only if balance >= kopeks; if not, log and bail
  UPDATE public.user_accounts
     SET balance_kopeks = balance_kopeks - p_kopeks
   WHERE user_id = p_user_id AND balance_kopeks >= p_kopeks;

  IF NOT FOUND THEN
    RAISE NOTICE '[billing] charge skipped: insufficient balance user=% job=% kopeks=%', p_user_id, p_job_id, p_kopeks;
    RETURN;
  END IF;

  INSERT INTO public.billing_charges (media_job_id, user_id, kopeks, kind, model_tier)
  VALUES (p_job_id, p_user_id, p_kopeks, p_kind, p_model_tier);
END;
$$;

-- Trigger: charge on media_jobs status transitions to 'completed'
CREATE OR REPLACE FUNCTION public.tg_billing_charge_on_complete()
RETURNS trigger
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = '', pg_catalog, public
AS $$
DECLARE
  v_kopeks bigint;
  v_model_tier text;
BEGIN
  IF NEW.status <> 'completed' OR OLD.status = 'completed' THEN
    RETURN NEW;
  END IF;

  v_model_tier := COALESCE((NEW.config_overrides->>'tier'), 'economy');
  v_kopeks := public.fn_price_kopeks(NEW.kind, v_model_tier);
  IF v_kopeks <= 0 THEN RETURN NEW; END IF;  -- free kind

  PERFORM public.fn_charge_balance(NEW.id, NEW.user_id, v_kopeks, NEW.kind, v_model_tier);
  RETURN NEW;
END;
$$;

CREATE TRIGGER trg_billing_charge_on_complete
  AFTER UPDATE OF status ON media_jobs
  FOR EACH ROW
  EXECUTE FUNCTION public.tg_billing_charge_on_complete();

-- Pure pricing function (mirrors KIND_PRICE_KOPEKS in @mango/core/quota/balance.ts)
CREATE OR REPLACE FUNCTION public.fn_price_kopeks(p_kind text, p_model_tier text)
RETURNS bigint
LANGUAGE sql
IMMUTABLE
AS $$
  SELECT CASE
    -- Image kinds — free for everyone
    WHEN p_kind IN ('character_dossier','character_avatar','character_reference','character_reference_image','first_frame','scene_first_frame') THEN 0
    -- Internal kinds — server chain, never user-charged
    WHEN p_kind IN ('last_frame_extract','storage_mirror') THEN 0
    -- Legacy audio kinds — disabled post-1.5 audio rip-out
    WHEN p_kind IN ('voice','scene_voice','final_clip','scene_final_clip') THEN 0
    -- Video kinds
    WHEN p_kind IN ('video','scene_video') AND p_model_tier = 'economy' THEN 5000   -- 50 ₽
    WHEN p_kind IN ('video','scene_video') AND p_model_tier = 'premium' THEN 25000  -- 250 ₽
    -- Master clip composition (ffmpeg)
    WHEN p_kind = 'master_clip' THEN 1000  -- 10 ₽
    ELSE 0
  END;
$$;
```

**Pricing rationale** (numbers chosen to give 2x margin over `cost_usd` at 90 ₽/USD):
- Economy scene (Grok Imagine 480p, ~$0.25/scene) → 50 ₽ ≈ 2.2x markup
- Premium scene (Seedance 2.0 10s, ~$1.1/scene) → 250 ₽ ≈ 2.5x markup
- Master clip (ffmpeg concat, ~$0.05/job) → 10 ₽ ≈ 2.2x markup

Top-up packages:
- `topup_2000` → 2000 ₽ → 40 economy scenes OR 8 premium scenes
- `topup_5000` → 5000 ₽ → 100 economy OR 20 premium
- `topup_10000` → 10000 ₽ → 200 economy OR 40 premium

(No discount/bonus on packages in 1.7; can add in 1.7.1 if conversion is low.)

### 3.2 `@mango/core/quota/balance.ts` (new module)

```typescript
export type ModelTier = 'economy' | 'premium';

export interface PriceQuote {
  kopeks: number;
  kind: MediaJobKind;
  model_tier: ModelTier | null;
}

export class BalanceGateError extends Error {
  readonly code = 'insufficient_balance' as const;
  readonly required_kopeks: number;
  readonly current_kopeks: number;
  readonly kind: MediaJobKind;
  constructor(opts: { required_kopeks: number; current_kopeks: number; kind: MediaJobKind }) {
    super(`insufficient_balance: ${opts.kind} requires ${opts.required_kopeks} kopeks, have ${opts.current_kopeks}`);
    this.name = 'BalanceGateError';
    this.required_kopeks = opts.required_kopeks;
    this.current_kopeks = opts.current_kopeks;
    this.kind = opts.kind;
  }
}

/**
 * Pure pricing — mirrors fn_price_kopeks() in the DB (keep in sync).
 */
export function priceKopeks(kind: MediaJobKind, modelTier?: ModelTier): number {
  // Image kinds — free
  if (kind === 'character_dossier' || kind === 'character_avatar' || kind === 'character_reference' || kind === 'character_reference_image' || kind === 'first_frame' || kind === 'scene_first_frame') return 0;
  // Internal / legacy audio — never user-charged
  if (kind === 'last_frame_extract' || kind === 'storage_mirror') return 0;
  if (kind === 'voice' || kind === 'scene_voice' || kind === 'final_clip' || kind === 'scene_final_clip') return 0;
  // Video kinds
  if (kind === 'video' || kind === 'scene_video') {
    return modelTier === 'premium' ? 25000 : 5000;
  }
  if (kind === 'master_clip') return 1000;
  const _u: never = kind;
  void _u;
  return 0;
}

export function assertBalance(
  balance_kopeks: number,
  kind: MediaJobKind,
  modelTier?: ModelTier,
): void {
  const required = priceKopeks(kind, modelTier);
  if (required <= 0) return;  // free kind
  if (balance_kopeks < required) {
    throw new BalanceGateError({ required_kopeks: required, current_kopeks: balance_kopeks, kind });
  }
}
```

### 3.3 Server-action gate rewrite

`generateSceneVideoAction`, `generateFirstFrameAction` (bulk path), `generateMasterClipAction` currently call `assertCapabilityOrLog(tier, kind, modelTier)`. v1.7 keeps that call (for the legacy `tier='trial'` anon block) AND adds a balance check:

```typescript
// existing
assertCapabilityOrLog(accountTier, 'scene_video', effectiveTier);

// new in 1.7
const balance = await getBalance(sb, user.id);
try {
  assertBalance(balance, 'scene_video', effectiveTier);
} catch (err) {
  if (err instanceof BalanceGateError) {
    return {
      ok: false,
      error: 'insufficient_balance',
      insufficient_balance: {
        required_kopeks: err.required_kopeks,
        current_kopeks: err.current_kopeks,
        kind: err.kind,
      },
    } as const;
  }
  throw err;
}
```

Mirrors the v1.6 `tier_gate` result shape pattern (non-breaking discriminated union).

Trial users (anon) still get blocked at the capability layer FIRST — they never reach the balance check. Free-tier authed users now hit balance gate.

### 3.4 ЮKassa integration

**SDK:** none — use raw HTTP. ЮKassa REST API is simple, the npm `@a2seven/yoo-checkout` SDK adds a 200kB dep for one POST and one webhook handler. Hand-roll.

**Server action** `createTopupAction({ package_code })` (`apps/web/src/app/upgrade/actions/createTopupAction.ts`):
1. Validate `package_code ∈ {'topup_2000','topup_5000','topup_10000'}`
2. Require authed email user (`redirect('/login')` if anon)
3. Generate idempotency key `crypto.randomUUID()`
4. POST to `https://api.yookassa.ru/v3/payments` with:
   - Basic auth: `YOOKASSA_SHOP_ID:YOOKASSA_SECRET_KEY`
   - `Idempotence-Key` header
   - body:
     ```json
     {
       "amount": { "value": "2000.00", "currency": "RUB" },
       "confirmation": { "type": "redirect", "return_url": "https://mangopro.ru/profile" },
       "capture": true,
       "description": "Mango Studio — 2000 ₽ top-up",
       "metadata": { "user_id": "<uuid>", "package_code": "topup_2000" }
     }
     ```
5. INSERT `billing_payments` row with `status='pending'`, `provider_payment_id=<yookassa.id>`
6. Return `{ ok: true, confirmation_url: <yookassa.confirmation.confirmation_url> }`
7. Client `window.location.replace(confirmation_url)`

**Webhook** `apps/web/src/app/api/webhooks/yookassa/route.ts`:
- POST handler
- Verify `Idempotence-Key` (ЮKassa retries on 5xx; same key = same payment intent)
- Verify request authenticity: ЮKassa uses **IP whitelist** (185.71.76.0/27, 185.71.77.0/27, 77.75.153.0/25, 77.75.154.128/25, 2a02:5180::/32) instead of HMAC signatures. Compare `x-forwarded-for` (Vercel populates) against the allowlist.
- Parse event: `payment.succeeded` → call `fn_apply_topup(payment_id, user_id, amount_kopeks)`
- Other events (`payment.canceled`, `payment.waiting_for_capture`) → just UPDATE `billing_payments.status`
- Return 200 OK on success, 500 on transient failure (ЮKassa retries up to 24h)

### 3.8 Refunds / failures

- **Refunds (manual ops)** — operator runs SQL: `UPDATE billing_payments SET status='refunded'` + `UPDATE user_accounts SET balance_kopeks = balance_kopeks - amount_kopeks WHERE user_id = ...`. Logged in `docs/audits/refund-YYYY-MM-DD-<payment_id>.md`. No self-service refund UI in 1.7.
- **Failed job (status='error') after charge** — no auto-credit-back in 1.7 (operator decides per-case). Future: trg_uncharge_on_error.
- **Partial failures (master_clip succeeds, scene fails halfway)** — each scene charged independently on its own completion; master_clip charges separately when master completes. No "all-or-nothing" guarantee.

## 4. Feature flags / rollout (G + H)

Three flags (env vars, default off):
- `NEXT_PUBLIC_PAYMENTS_UI_ENABLED` — gates `/upgrade` page + ProfileCard top-up button + InsufficientBalanceModal. Off → users see existing v1.6.2 UI.
- `PAYMENTS_GATE_ENFORCE` — wraps `assertBalance` in `assertBalanceOrLog` (canary). Off → log only, video proceeds.
- `YOOKASSA_LIVE` — `false` = sandbox shop_id + endpoint, `true` = live. Webhook handler picks endpoint based on env.

Rollout phases (similar to v1.6 H1-H3):
- H1 — open PR with flags OFF; merge → Vercel deploy; no behavior change for users
- H2 — flip `NEXT_PUBLIC_PAYMENTS_UI_ENABLED=true` (UI visible but gate still log-only); operator tops up own account via ЮKassa sandbox; verify webhook fires + balance increments; flip to live ЮKassa
- H3 — flip `PAYMENTS_GATE_ENFORCE=true` (enforcement live); E2E checklist; tag `v1.7.0`

## 6. Risks + open questions

**Risks:**
1. **Webhook replay attack** — solved by `Idempotence-Key` + `billing_payments.status='pending'` guard in `fn_apply_topup`.
2. **Race between webhook + user submit** — user could top up, webhook arrives after their next video attempt fails. Mitigation: show toast on `/profile?topup=success` saying "Баланс обновится в течение минуты".
3. **Currency drift** — kopeks in DB / RUB in ЮKassa / USD in `cost_usd` for analytics. Always convert via `Math.round(usd * 9000)` (90 ₽/USD assumed). No FX gate in 1.7; if USD/RUB drifts >20% revisit prices.
4. **Refund creates negative balance** — `CHECK (balance_kopeks >= 0)` on table blocks NEGATIVE row. Refund op MUST verify `balance >= refund_amount` first; otherwise pay refund out-of-band and write off the balance debt.
5. **ЮKassa downtime** — `createTopupAction` returns error; user retries. Webhook delivery is at-least-once, so retried events are safe.
6. **Sandbox→live cutover** — both shop_id and secret differ; `YOOKASSA_LIVE` flag drives both. Webhook URL is the same (`/api/webhooks/yookassa`) — ЮKassa dashboard configures live webhook to the same URL. Operator must re-test after flip.

**Open questions (executor decides):**
- Toast UX on `/profile?topup=success` — server-action redirect vs client-side query string parse
- "Пополнить" link in AccountMenu — always shown or only when balance < 100 ₽?
- Anon middleware behavior on `/upgrade` — block (redirect to /login) per v1.6 pattern OR show "войдите чтобы пополнить" CTA inline. Recommendation: redirect (consistent with /profile).
- Per-IP rate limit on `createTopupAction` — relying on F53 atomic media-job limit OR add new throttle. Default: rely on F53 + ЮKassa's own rate limits.

## 9. Cross-cutting standards (carried from v1.6)

- All server actions return `{ok:true,...} | {ok:false, error:string, ...}` discriminated union (RSC error masking workaround from v1.5.1)
- All DB writes go through `service_role` (server-action layer) — never client-direct
