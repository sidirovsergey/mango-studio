# Phase 1.7 — Payments (credit balance + ЮKassa top-ups)

**Date:** 2026-05-17 (brainstorm done immediately after v1.6.2 ship)
**Status:** spec v2 — Codex audit pass 1 closed (4 BLOCKER / 8 SHOULD-FIX / 2 NIT applied)
**Goal:** Replace the binary `premium` tier in v1.6 with a per-user kopek-precision **credit balance** that gates video generation. Top-ups via **ЮKassa** (RU карты + СБП). No subscription in 1.7.

## 1. Motivation

v1.6 shipped tier-based gating with `trial / free / premium` enum on `user_accounts`. The original plan had Phase 1.7 = "wire payments to flip tier to premium" (monthly subscription).

User pivoted during 1.7 brainstorm (this session): replace the subscription model with **prepaid credit balance**. Rationale:
- Lower commitment for first-time users (one-time top-up, not recurring)
- Marketplace alignment — Russian B2C audience prefers credit packages to subscriptions
- Pricing flexibility — each video model has different cost basis (Seedance vs Veo vs Grok Imagine differ ~10x in per-generation cost); credits give us per-operation pricing without renegotiating a subscription tier
- Refund simplicity — credits don't expire; if user is unhappy we just zero the row, no proration

The tier-based capability matrix from v1.6 stays as a **fallback discriminator** for non-paid features (legacy audio kinds, internal kinds), but the user-visible video gate becomes balance-based.

```sql
ALTER TABLE user_accounts
  ADD COLUMN balance_kopeks bigint NOT NULL DEFAULT 0 CHECK (balance_kopeks >= 0);

-- Payment intents (one per ЮKassa Payment.create call)
CREATE TABLE billing_payments (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id uuid NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  provider text NOT NULL DEFAULT 'yookassa' CHECK (provider IN ('yookassa')),
  provider_payment_id text NOT NULL UNIQUE,  -- ЮKassa idempotency key
  amount_kopeks bigint NOT NULL CHECK (amount_kopeks > 0),
  currency text NOT NULL DEFAULT 'RUB' CHECK (currency IN ('RUB')),
  status text NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','succeeded','canceled','failed','refunded')),
  package_code text NOT NULL CHECK (package_code IN ('topup_2000','topup_5000','topup_10000')),
  created_at timestamptz NOT NULL DEFAULT now(),
  succeeded_at timestamptz,
  metadata jsonb NOT NULL DEFAULT '{}'::jsonb  -- ЮKassa raw response
);

CREATE INDEX billing_payments_user_id_created_at_idx
  ON billing_payments (user_id, created_at DESC);

-- Charges (one per reserved media_job; tracks lifecycle reserved → charged | refunded)
-- This IS the held-balance ledger that prevents concurrent-submit race

  user_id uuid NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  kopeks bigint NOT NULL CHECK (kopeks > 0),

  settled_at timestamptz

CREATE INDEX billing_charges_user_id_created_at_idx
  ON billing_charges (user_id, created_at DESC);

-- RLS: clients read own rows only; writes via SECURITY DEFINER
ALTER TABLE billing_payments ENABLE ROW LEVEL SECURITY;
ALTER TABLE billing_charges  ENABLE ROW LEVEL SECURITY;

  FOR SELECT USING (user_id = auth.uid());

-- Atomic top-up function (called from webhook).
-- Codex BLOCKER #2: derives user_id + amount from the stored billing_payments
-- row (looked up by provider_payment_id), NOT caller-supplied. This means
-- a forged webhook body cannot credit a different user or a different
-- amount than what the operator's createTopupAction recorded.
-- Codex BLOCKER #4: requires a pending billing_payments row to exist;
-- returns silently for unknown provider_payment_id (treat as no-op replay).
-- Codex SHOULD-FIX #1: uses CTE so the SELECT, UPDATE billing_payments,
-- and UPDATE user_accounts are one statement (no read-then-write race).
CREATE OR REPLACE FUNCTION public.fn_apply_topup(
  p_provider_payment_id text,
  p_observed_amount_kopeks bigint  -- amount reported by webhook event body
) RETURNS void
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = '', pg_catalog, public
AS $$
DECLARE
  v_row record;
BEGIN
  WITH locked AS (
    SELECT id, user_id, amount_kopeks, status
      FROM public.billing_payments
     WHERE provider_payment_id = p_provider_payment_id
     FOR UPDATE
  ), promoted AS (
    UPDATE public.billing_payments
       SET status = 'succeeded',
           succeeded_at = COALESCE(succeeded_at, now())
     WHERE id = (SELECT id FROM locked WHERE status = 'pending')
    RETURNING id, user_id, amount_kopeks
  )
  SELECT * INTO v_row FROM promoted;

  IF v_row.id IS NULL THEN
    -- No pending row matched: either replay (already succeeded) or
    -- terminal-state mismatch (already canceled/refunded). Either way, no-op.
    RETURN;
  END IF;

  -- Defense-in-depth: webhook event body amount MUST match the amount we
  -- recorded when calling Payment.create. If ЮKassa returns a different
  -- amount (e.g. partial-capture flow), refuse the credit and leave the
  -- payment in 'succeeded' status but log the mismatch for ops review.
  IF v_row.amount_kopeks <> p_observed_amount_kopeks THEN
    RAISE WARNING '[billing] topup amount mismatch: payment=% recorded=% observed=%',
      v_row.id, v_row.amount_kopeks, p_observed_amount_kopeks;
    RETURN;
  END IF;

  UPDATE public.user_accounts
     SET balance_kopeks = balance_kopeks + v_row.amount_kopeks
   WHERE user_id = v_row.user_id;
END;
$$;

-- Atomic balance reservation function (called from server action at submit).
-- Codex BLOCKER #3 fix: atomically debit balance AND insert charges row in
-- one statement. If balance < kopeks, the UPDATE matches zero rows and
-- the INSERT is skipped via WHERE EXISTS. Returns BOOLEAN: true = reserved,
-- false = insufficient balance.
-- Codex SHOULD-FIX #1 fix: single CTE prevents read-then-write race;
-- INSERT...ON CONFLICT DO NOTHING handles trigger re-fire idempotency.
CREATE OR REPLACE FUNCTION public.fn_reserve_balance(
  p_job_id     uuid,
  p_user_id    uuid,
  p_kopeks     bigint,
  p_kind       text,
  p_model_tier text
) RETURNS boolean
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = '', pg_catalog, public
AS $$
DECLARE
  v_already int;
BEGIN
  -- Idempotency: if charges row already exists for this job, treat as ok
  -- (caller re-tried; nothing more to do).
  SELECT 1 INTO v_already FROM public.billing_charges WHERE media_job_id = p_job_id;
  IF FOUND THEN RETURN true; END IF;

  IF p_kopeks <= 0 THEN
    -- Free kind: insert a zero-cost charged row for audit completeness, OR
    -- just return true without writing. Skip write for free kinds — keeps
    -- the table tight.
    RETURN true;
  END IF;

  WITH debit AS (
    UPDATE public.user_accounts
       SET balance_kopeks = balance_kopeks - p_kopeks
     WHERE user_id = p_user_id AND balance_kopeks >= p_kopeks
    RETURNING user_id
  )
  INSERT INTO public.billing_charges (media_job_id, user_id, kopeks, kind, model_tier, status)
  SELECT p_job_id, user_id, p_kopeks, p_kind, p_model_tier, 'reserved' FROM debit
  ON CONFLICT (media_job_id) DO NOTHING;

  -- If the INSERT happened (row count > 0), reservation succeeded.
  RETURN FOUND;
END;
$$;

-- Refund a previously-reserved charge (called from trigger when media_job
-- moves to terminal error/canceled). Idempotent via status guard.
CREATE OR REPLACE FUNCTION public.fn_refund_reservation(
  p_job_id uuid
) RETURNS void
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = '', pg_catalog, public
AS $$
DECLARE
  v_row record;
BEGIN
  WITH refunded AS (
    UPDATE public.billing_charges
       SET status = 'refunded',
           settled_at = now()
     WHERE media_job_id = p_job_id
       AND status = 'reserved'
    RETURNING user_id, kopeks
  )
  SELECT * INTO v_row FROM refunded;

  IF v_row.user_id IS NULL THEN RETURN; END IF;

  UPDATE public.user_accounts
     SET balance_kopeks = balance_kopeks + v_row.kopeks
   WHERE user_id = v_row.user_id;
END;
$$;

-- Finalise a previously-reserved charge (called from trigger when media_job
-- moves to terminal completed). Just flips status — balance already debited
-- at reserve time. Idempotent via status guard.
CREATE OR REPLACE FUNCTION public.fn_finalise_charge(
  p_job_id uuid
) RETURNS void
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = '', pg_catalog, public
AS $$
BEGIN
  UPDATE public.billing_charges
     SET status = 'charged',
         settled_at = now()
   WHERE media_job_id = p_job_id
     AND status = 'reserved';
END;
$$;

-- Trigger: fire reservation finalise / refund based on media_jobs status transitions
CREATE OR REPLACE FUNCTION public.tg_billing_settle_on_terminal()
RETURNS trigger
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = '', pg_catalog, public
AS $$
BEGIN
  -- Only fire on transitions INTO terminal states from non-terminal source
  IF NEW.status = OLD.status THEN RETURN NEW; END IF;
  IF OLD.status IN ('completed','error','canceled') THEN RETURN NEW; END IF;

  IF NEW.status = 'completed' THEN
    PERFORM public.fn_finalise_charge(NEW.id);
  ELSIF NEW.status IN ('error','canceled') THEN
    PERFORM public.fn_refund_reservation(NEW.id);
  END IF;

  RETURN NEW;
END;
$$;

CREATE TRIGGER trg_billing_settle_on_terminal
  AFTER UPDATE OF status ON media_jobs
  FOR EACH ROW
  EXECUTE FUNCTION public.tg_billing_settle_on_terminal();

-- Pure pricing function (mirrors KIND_PRICE_KOPEKS in @mango/core/quota/balance.ts)
CREATE OR REPLACE FUNCTION public.fn_price_kopeks(p_kind text, p_model_tier text)
RETURNS bigint
LANGUAGE sql
IMMUTABLE
AS $$
  SELECT CASE
    -- Image kinds — free for everyone
    WHEN p_kind IN ('character_dossier','character_avatar','character_reference','character_reference_image','first_frame','scene_first_frame') THEN 0
    -- Internal kinds — server chain, never user-charged
    WHEN p_kind IN ('last_frame_extract','storage_mirror') THEN 0
    -- Legacy audio kinds — disabled post-1.5 audio rip-out
    WHEN p_kind IN ('voice','scene_voice','final_clip','scene_final_clip') THEN 0
    -- Video kinds
    WHEN p_kind IN ('video','scene_video') AND p_model_tier = 'economy' THEN 5000   -- 50 ₽
    WHEN p_kind IN ('video','scene_video') AND p_model_tier = 'premium' THEN 25000  -- 250 ₽
    -- Master clip composition (ffmpeg)
    WHEN p_kind = 'master_clip' THEN 1000  -- 10 ₽
    ELSE 0
  END;
$$;

-- =====================================================================
-- Codex BLOCKER #1: lock down SECURITY DEFINER fns
-- All billing functions must run via service_role only (webhook handler

REVOKE EXECUTE ON FUNCTION public.fn_apply_topup(text, bigint) FROM PUBLIC, anon, authenticated;
```

### 3.2 `@mango/core/quota/balance.ts` (new module)

```typescript
export type ModelTier = 'economy' | 'premium';

export interface PriceQuote {
  kopeks: number;
  kind: MediaJobKind;
  model_tier: ModelTier | null;
}

export class BalanceGateError extends Error {
  readonly code = 'insufficient_balance' as const;
  readonly required_kopeks: number;
  readonly current_kopeks: number;
  readonly kind: MediaJobKind;
  constructor(opts: { required_kopeks: number; current_kopeks: number; kind: MediaJobKind }) {
    super(`insufficient_balance: ${opts.kind} requires ${opts.required_kopeks} kopeks, have ${opts.current_kopeks}`);
    this.name = 'BalanceGateError';
    this.required_kopeks = opts.required_kopeks;
    this.current_kopeks = opts.current_kopeks;
    this.kind = opts.kind;
  }
}

/**
 * Pure pricing — mirrors fn_price_kopeks() in the DB (keep in sync).
 */
export function priceKopeks(kind: MediaJobKind, modelTier?: ModelTier): number {
  // Image kinds — free
  if (kind === 'character_dossier' || kind === 'character_avatar' || kind === 'character_reference' || kind === 'character_reference_image' || kind === 'first_frame' || kind === 'scene_first_frame') return 0;
  // Internal / legacy audio — never user-charged
  if (kind === 'last_frame_extract' || kind === 'storage_mirror') return 0;
  if (kind === 'voice' || kind === 'scene_voice' || kind === 'final_clip' || kind === 'scene_final_clip') return 0;
  // Video kinds
  if (kind === 'video' || kind === 'scene_video') {
    return modelTier === 'premium' ? 25000 : 5000;
  }
  if (kind === 'master_clip') return 1000;
  const _u: never = kind;
  void _u;
  return 0;
}

export function assertBalance(
  balance_kopeks: number,
  kind: MediaJobKind,
  modelTier?: ModelTier,
): void {
  const required = priceKopeks(kind, modelTier);
  if (required <= 0) return;  // free kind
  if (balance_kopeks < required) {
    throw new BalanceGateError({ required_kopeks: required, current_kopeks: balance_kopeks, kind });
  }
}
```

### 3.4 ЮKassa integration

**SDK:** none — use raw HTTP via `fetch`. ЮKassa REST API is simple (1 POST + 1 webhook); npm `@a2seven/yoo-checkout` adds ~200kB dep for that. Hand-roll.

**Server action** `createTopupAction({ package_code })` (`apps/web/src/app/upgrade/actions/createTopupAction.ts`):
1. Validate `package_code ∈ {'topup_2000','topup_5000','topup_10000'}` (Zod safeParse)
2. Require authed email user (`redirect('/login')` if anon)
3. **Idempotence-Key (Codex SHOULD-FIX #5)**: deterministic per-user-per-package-per-minute key so a double-click within 60s returns the SAME ЮKassa payment intent. Algorithm: `topup:${user.id}:${package_code}:${Math.floor(Date.now() / 60_000)}`. No external cache needed — ЮKassa de-duplicates server-side via this header per their docs.
4. POST to `https://api.yookassa.ru/v3/payments` with:
   - Basic auth: `${YOOKASSA_SHOP_ID}:${YOOKASSA_SECRET_KEY}` → base64
   - `Idempotence-Key: ${deterministic-key}` header
   - body:
     ```json
     {
       "amount": { "value": "2000.00", "currency": "RUB" },
       "confirmation": { "type": "redirect", "return_url": "https://mangopro.ru/profile?topup=pending" },
       "capture": true,
       "description": "Mango Studio — пополнение баланса на 2000 ₽",
       "metadata": { "user_id": "<uuid>", "package_code": "topup_2000" },
       "receipt": {
         "customer": { "email": "<user.email>" },
         "items": [{
           "description": "Пополнение баланса Mango Studio",
           "quantity": "1.00",
           "amount": { "value": "2000.00", "currency": "RUB" },
           "vat_code": 1,
           "payment_subject": "service",
           "payment_mode": "full_payment"
         }]
       }
     }
     ```
   - **Codex SHOULD-FIX #3 — 54-ФЗ receipt**: the `receipt` block is REQUIRED by Russian fiscalisation law (Federal Law 54-ФЗ) for any operator accepting card payments from physical persons. Without it ЮKassa returns HTTP 400 OR (worse, in test mode) accepts the payment but later the operator gets fined. `vat_code: 1` = "без НДС" (НДС не облагается, applies to СМЗ self-employed); `payment_subject: 'service'` = digital service. If operator status changes (e.g. ИП on УСН), `vat_code` may need to flip — verify with accountant before live cutover.
5. INSERT `billing_payments` row: `provider_payment_id = <yookassa.id>`, `status='pending'`, `amount_kopeks`, `package_code`, `metadata = <yookassa raw response>`.
6. Return `{ ok: true, confirmation_url: <yookassa.confirmation.confirmation_url> }`.
7. Client: `window.location.replace(confirmation_url)`.

  ```typescript
    // the FIRST entry is the original client. Trim whitespace + strip
    // possible port suffix.
    const xff = req.headers.get('x-forwarded-for') ?? '';
    const first = xff.split(',')[0]?.trim();
    if (!first) return null;
    // Strip IPv4 port (e.g. "1.2.3.4:5678") — IPv6 has port only in brackets
    return first.includes(':') && first.startsWith('[') ? first.split(']')[0]?.slice(1) ?? null : first.split(':')[0] ?? first;
  }
  // YOOKASSA_ALLOWED_CIDRS hard-coded from
  // https://yookassa.ru/developers/using-api/webhooks#ip
  // Match with the `ipaddr.js` package (npm, ~10kB) which handles both
  // IPv4 and IPv6 CIDR notation correctly. Reject (HTTP 403) if no match.
  ```
- **Codex BLOCKER #4 — webhook lookup**: parse event body, extract `event.object.id` as `provider_payment_id` and `event.object.amount.value` as observed amount. Call `fn_apply_topup(provider_payment_id, Math.round(parseFloat(value) * 100))`. The function looks up the stored `billing_payments` row by `provider_payment_id`, derives `user_id` and `amount_kopeks` from THAT row (not from webhook body), and validates the observed amount matches before crediting.
- Events:
  - `payment.succeeded` → `fn_apply_topup(...)` (credits balance)
  - `payment.canceled` → `UPDATE billing_payments SET status='canceled' WHERE provider_payment_id = ...`
  - `payment.waiting_for_capture` → log + UPDATE status (rare with `capture: true`)
  - Unknown event → 200 OK, log + ignore (forward-compat)
- Return 200 OK on success (even for "already succeeded" no-op replays — ЮKassa stops retrying on 200), 500 on transient DB/network failure (ЮKassa retries up to 24h with exponential backoff).

### 3.8 Refunds / failures

- **Failed media-job (status='error' or 'canceled')** — `trg_billing_settle_on_terminal` calls `fn_refund_reservation(job_id)`, which credits balance back atomically. User never pays for failed video. Idempotent via `status='reserved'` guard.
- **Top-up refund (manual ops)** — operator runs the following **transactional, guarded** SQL (Codex SHOULD-FIX #8 fix):

  ```sql
  BEGIN;

  -- Step 1: lock the payment row, verify it's currently 'succeeded'
  SELECT id, user_id, amount_kopeks
    FROM billing_payments
   WHERE id = '<payment_uuid>' AND status = 'succeeded'
     FOR UPDATE;
  -- If no row → already refunded or never succeeded; abort: ROLLBACK;

  -- Step 2: atomic balance debit GUARDED by balance >= refund amount
  -- If FOUND, balance is debited; if NOT FOUND, the operator must
  -- pay refund out-of-band and write off the balance debt (the
  -- balance was already spent on videos and cannot be clawed back).
  UPDATE user_accounts
     SET balance_kopeks = balance_kopeks - <amount_kopeks>
   WHERE user_id = '<user_uuid>'
     AND balance_kopeks >= <amount_kopeks>
  RETURNING balance_kopeks;
  -- 0 rows = insufficient balance; operator decides — see audit doc

  -- Step 3: flip payment status (only if step 2 succeeded)
  UPDATE billing_payments
     SET status = 'refunded'
   WHERE id = '<payment_uuid>';

  -- Step 4: trigger ЮKassa refund via dashboard or API (out-of-band)

  COMMIT;
  ```

  Operator MUST log every refund to `docs/audits/refund-YYYY-MM-DD-<payment_id>.md` with: payment_id, user email, amount, reason, whether step 2 succeeded or balance debt was written off, ЮKassa refund ID. No self-service refund UI in 1.7.

- **Partial failures (master_clip succeeds, scene fails halfway)** — each scene charged independently on its own reserve; master_clip charges separately when its own reserve succeeds. Failed scenes refund automatically; succeeded scenes stay charged. No "all-or-nothing" guarantee at the project level — too complex for 1.7, deferred.

## 6. Risks + open questions

**Risks (post-Codex revision):**
1. **Webhook replay attack** — solved by `Idempotence-Key` (deterministic, 60s window) + `billing_payments.status='pending'` guard in `fn_apply_topup` (CTE atomic). Codex BLOCKER #2/#4 closed.
2. **Webhook body forgery** — `fn_apply_topup` derives `user_id` and `amount_kopeks` from the LOOKED-UP `billing_payments` row by `provider_payment_id`, not from caller args. Even if attacker gets past IP allowlist, they can't credit another user or a fake amount. Observed amount cross-checked against stored amount; mismatch logs warning + skips credit. Codex BLOCKER #2 closed.
3. **Concurrent submit race (drain balance)** — solved by `fn_reserve_balance` (atomic UPDATE...WHERE balance>=kopeks + INSERT...ON CONFLICT in one CTE statement). If two submits land simultaneously with balance=100 and price=60, the first UPDATE succeeds (balance=40), the second fails the WHERE → 0 rows → INSERT skipped → server-action returns `insufficient_balance`. No double-spend. Codex BLOCKER #3 closed.
4. **Service-role bypass via RPC** — `REVOKE EXECUTE ... FROM PUBLIC, anon, authenticated` + explicit `GRANT EXECUTE ... TO service_role` on all billing functions. Even a compromised anon JWT cannot call `fn_apply_topup`, `fn_reserve_balance`, etc. via supabase-js RPC. Codex BLOCKER #1 closed.
5. **Race between webhook + user submit** — user could top up, webhook arrives mid-flow. Mitigation: toast on `/profile?topup=pending` says "Баланс обновится в течение минуты", auto-refreshes via Realtime subscription on `user_accounts.balance_kopeks` change OR a 5-sec poll.
6. **Currency drift** — kopeks in DB / RUB in ЮKassa / USD in `cost_usd` for analytics. Always convert via `Math.round(usd * 9000)` (90 ₽/USD assumed). No FX gate in 1.7; if USD/RUB drifts >20% revisit prices.
7. **Refund creates negative balance** — `CHECK (balance_kopeks >= 0)` on table blocks NEGATIVE row. Refund SQL (§3.8) is now transactional + guarded with `balance >= amount_kopeks`; if NOT FOUND, operator decides per-case (refund out-of-band, write off balance debt).
8. **54-ФЗ non-compliance** — operator fined if receipt data missing in production payments. `receipt` block required in `Payment.create` body. `vat_code` depends on operator legal status; verify with accountant before live cutover. Codex SHOULD-FIX #3 closed.
9. **Pricing parity drift (SQL fn vs TS module)** — parity test in `packages/core/src/quota/balance.parity.test.ts` runs CI gate against migrated test DB; bumping one without the other fails CI. Codex SHOULD-FIX #2 closed.
10. **ЮKassa downtime** — `createTopupAction` returns error; user retries. Webhook delivery is at-least-once, so retried events are safe.
11. **Sandbox→live cutover** — both shop_id and secret differ; `YOOKASSA_LIVE` flag drives both. Webhook URL is the same (`/api/webhooks/yookassa`) — ЮKassa dashboard configures live webhook to the same URL. Operator must re-test after flip.
12. **Manual canceled rollback gap** — if `fn_reserve_balance` succeeds but the subsequent `await sb.from('media_jobs').update({status:'canceled'})` for the rollback path fails (network), the user has a "reserved" charge with no completion path. Mitigation: cron sweep `trg_billing_settle_on_terminal` candidates older than 1h still in `status='reserved'` → auto-refund. Deferred to 1.7.1 if observed.

**Open questions (executor decides):**
- Toast UX on `/profile?topup=success` — server-action redirect vs client-side query string parse
- "Пополнить" link in AccountMenu — always shown or only when balance < 100 ₽?
- Anon middleware behavior on `/upgrade` — block (redirect to /login) per v1.6 pattern OR show "войдите чтобы пополнить" CTA inline. Recommendation: redirect (consistent with /profile).
